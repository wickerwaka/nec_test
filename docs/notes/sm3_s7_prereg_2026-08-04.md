## §3 CELL (a) — **H1a**: is the arm the interrupt ENTRY or the INTA CYCLE?

§64.2 opened H1a on **2 seeds** with a registered falsifier and specified the
cell that would settle it: *"the `sm3_h1_cell` `iretnext` stimulus with the
pre-planted frames reached by a software `INT n` instead of by the rig's pin,
so the entry is real and carries no INTA."*  It is taken here.

**THE STIMULUS** — `sm3_h1_cell.py` variant **`swintnext`**: a chain of
`CD 20` (`INT SWINT_VEC`), whose IVT slot points at `far_int_support`'s bare
`CF` handler.  Validated OFFLINE through `sim/` before any board contact, and
it produces `mc1/2672`'s shape exactly:

```
  CODE:00500 CODE:00502 CODE:00504   MEMR:00080 MEMR:00082     <- the VECTOR read
  MEMW:03efe MEMW:03efc MEMW:03efa                             <- the entry's frame
  CODE:00480 CODE:00482                                        <- the bare IRET handler
  MEMR:03efa MEMR:03efc MEMR:03efe                             <- the IRET's three pops
  CODE:00502                                                   <- the RESTARTED prefetch
```

It is **self-selecting**: IE is CLEAR from the entry until the IRET restores
it, so the ONLY boundary in the whole stream at which a maskable INT can be
recognised is the one immediately after each IRET's restarted prefetch — which
is exactly the boundary H1a is about.  **`iretnext` is the CONTROL**: the same
IRET, the same restarted prefetch, popping PRE-PLANTED frames, with **no entry
of any kind behind it**.

**THE OBSERVABLE**, off the pins, no engine: `refill_gap` — the clocks from the
restarted prefetch's T1 to the FIRST acknowledge's T1.  H1's floor is
`max(F1 + 6, F1 + L + 1)`; the restart's `L` is 4, so **FLOORED = 6** and
**UNFLOORED = 4**.  Two clocks.

`sm3_h1_cell.py h1a` also classifies each first acknowledge's lead-in
(`entry_shape`) into `swint-entry` / `iret-only` / `inta-behind` / `other`, so
a capture whose acknowledge did not land where the stimulus intends is
EXCLUDED by its own shape rather than by hand.

**THE CANDIDATES AND THEIR PREDICTIONS.**

| | `swintnext` first acknowledges | `iretnext` first acknowledges |
|---|---|---|
| **A1 — the arm is the interrupt ENTRY SEQUENCE** | **FLOORED**, `refill_gap` = `max(6, L+1)` | **UNFLOORED**, `refill_gap` = `L` |
| **A2 — the arm is the INTA BUS CYCLE** (what both engines implement today) | **UNFLOORED**, `refill_gap` = `L` | **UNFLOORED**, `refill_gap` = `L` |

* **AUTHORISING OUTCOME (A1)**: `>= 95 %` of `swint-entry`-shaped first
  acknowledges FLOORED **at every wait level 0-3**, AND `>= 95 %` of
  `iret-only`-shaped ones UNFLOORED.  Both halves are required: the control is
  what makes the arm about the ENTRY rather than about the IRET.
* **REFUTING OUTCOME (A2)**: `>= 95 %` of `swint-entry` first acknowledges
  UNFLOORED.  **H1a is then REFUTED** and §64.2's two seeds are recorded as
  coincidence at n = 2, exactly as its registered falsifier says.
* **INCONCLUSIVE**: anything else, including a split by wait level.  Reported
  as inconclusive; nothing is landed on a split.

**WHAT AN A1 VERDICT DOES AND DOES NOT AUTHORISE.**  It does **NOT** authorise
an address-keyed rule — §64.2 rejected *"arm on a `MEMR` below `0x400`"* as a
fitted table with no mechanism, and that judgement stands.  What it authorises
is the MECHANISM-LEVEL shape and only that: **the EU already runs one
microcoded interrupt-entry sequence for every entry** (INTA-announced or
vector-read; the part does not have two), so the arm becomes *"the EU's
interrupt-entry microcode started"*, PUBLISHED BY THE EU and consumed by the
BIU — one wire in `hdl/rtl/ucore/`, the same construction F43 used, and the
corresponding one-line hook in `sim/`.  It strictly GENERALISES today's arm
(an INTA entry runs the same microcode), which is what makes it a candidate at
all.

**IF IT IS LANDED, THE MUST-NOT-MOVE LIST IS THE FULL LADDER** and it is
registered here in advance: `check_core --core ucore --opcodes all --cases 0`
**169,000 / 169,000**; `v0.1-w1` / `-w3` **1,200 / 1,200**; `EB` at w1 **200**;
the four `evt` cells **200 / 1,200 / 200 / 1,200**; `v0.1-w1evt-biased`
**1,200**; `f4a_boundary` **160**; `f0lock_tranche` **400**; the 23 `v0.3`
block-I/O forms **229,999**; `check_boot --core ucore` **220 and 400**;
`ulockstep --golden all --cases 50` **17,350 / 17,350**;
`timed_wvec_gate --core ucore` **88/88, +0.0 %**;
`timed_enter_replay --core ucore` **154/154 ×5**;
`timed_ins_replay --core ucore --raw` **1,312 / 2,624**;
`ss_lint` rc 0 / 0 UNMAPPED; `check_core --ce-div 4 --ce-hold-check`

## §4 CELL (b) — **H7-boundary**: does the OPCODE at the boundary select the floor?

§65.1's lead: *"The selector is not on the pin side; it is WHICH INSTRUCTION'S
BOUNDARY the recognition lands on."*  It converged from three directions, all

### §4.1 The board-free census that SELECTED the opcode set

New MEASUREMENT tool (never a gate): **`sw/sm3_h7_opcode.py`**.  It reads the
opcode at the recognition boundary CHIP-SIDE, with no engine in the loop, off
the `QS` port alone: `E` flushes, `F` pops an instruction's first byte, `S` a
subsequent byte, and queue bytes are consumed in ascending address order from
the fetch after the last flush — so ONE POINTER names the image byte every pop
consumed.  Run over the 208 banked NMI seeds (193 with a recognition,
**0 unplaced pops**), it is the measurement §65.1 specified and did not take.

Its result is recorded here as the census that CHOSE the opcodes, and it is
**not** the cell's evidence:

* the chip's `gap = V − A` histogram reproduces §63.2 exactly — **12 : 30,
  13 : 18**;
* **no opcode partitions the two camps.**  `B9`, `CF`, `EA`, `E9` appear at
  both;
* **`90` (NOP) appears at gap 12 on FOUR banked seeds** — verified by hand on
  `mc1/raw_3571`, where the image is a solid `90` sled and the recognition
  sits at `A + 12` — while §65.1's directed NOP-sled cell floors at **13** over
  40 captures, and the golden `NMI.90` is A-limited at 13;
* a new coordinate the lead did not predict: the floor population is
  **BANK-ASSOCIATED** — `mc2` has **0 of 75** at gap 12, `mc1` **26 of 85**,
  `t30-raw` **4 of 33**.  `gen_git` tracks the bank exactly, so this is a
  property of the two generators' programs, not of a capture era (`banked_ts`
  is the same day for all 193).

### §4.2 The cell

## §5 CELL (c) — **H3 class B**: the WAIT-VECTOR walk

§65.2 missed its family (`R4`, **0** same-clock/different-owner pairs on 3,744
accesses against BOTH engines) and said why: the `EB 00` flush resynchronises
the refill, so every access is preceded by a `CODE` fetch on 312/312, and the
pad moves the EU request in WHOLE BYTES — 2 to 3 clocks at a time.  The EU
request never lands ON the prefetcher's eligibility instant.  Its spec for the
cell that would reach it: *"the same body with the EU request moved in CLOCK
steps rather than byte steps — a per-access wait vector on the fetch
immediately preceding the access."*

**THE RIG CAN EXPRESS IT, VERIFIED IN THE RTL AND THE HOST PATH BEFORE
DESIGNING AROUND IT** (the work order's condition):
`hdl/rtl/nec_bus.sv`'s `cfg_wait_replay` + `wvec_buf` RAM,
`hdl/rtl/hps_axi_slave.sv` `wdata[1]`, and host-side
`v30run.Runner.replay(tw_list)` (`WVEC` + `WRAND - - - 1`), reached through
`run_image(..., wvec=...)`.  **`s10_board.capture()` did not pass it through;
this sitting adds the passthrough and nothing else.**  The SAME vector goes to
`sim/` (`--wvec`) and to the Verilator TB (`+wvec`); all three index it by
bus-cycle ordinal from run start (`sim/timed_runner.cpp:394` says so beside the
code, and `timed_wvec_gate`'s 88/88 against the chip baseline is the standing
evidence that the indices agree).

**THE VECTOR IS PERIODIC AND PHASE-SWEPT, not addressed by absolute ordinal**,
so it needs no prediction of where each access falls: `period` — the loop
body's bus-cycle count — is MEASURED off a uniform-waits baseline capture in
the same cell, and the vector puts `+extra` waits on the access `r` cycles
before every EU access.  **`r = 1, extra = 1` is §65.2's sentence verbatim**;
sweeping `r = 0 … period-1` walks it round, and `extra ∈ {1, 2}` displaces the
eligibility instant by one and by two clocks.  Stimuli: `mw`, `mwseg`, `mr` at
`pad = 3`, waits 0/1/2/3.

**THE BARS.**

* **R0 (the alignment control, and it gates everything else)** — the chip's
  ACHIEVED per-cycle wait count (cycle length − 4, read off the pins) must
  match the vector it was handed on **>= 95 %** of bus cycles.  Below that the
  three indices do not agree, **no conclusion is drawn from the cell**, and
  what is missing from the rig is written down instead.
* **S1 (the sweep is real)** — the phase sweep MOVES the EU access's lead-in
  gap in ONE-CLOCK steps: **>= 3 distinct `gap` values** per (variant, wait)
  pooled over `r`, against §65.2's coarse 2-3 values from whole-byte steps.
* **S2 (the family is reached)** — **>= 1** same-clock/different-owner pair
  against at least one engine, where §65.2 scored **0 / 3,744**.
* **S3 (the registered negative)** — S1 met, R0 met and S2 still **0** over
  **>= 3,000** paired accesses means class B is NOT reachable by a
  clock-resolution walk of the eligibility instant either.  That is a RESULT
  and it is reported as one; the family's residence is then somewhere this
  stimulus does not go, and the next spec is written from it.

**PREDICTION: R0 met, S1 met, S2 = 0 — i.e. S3.**  Class B is 184-of-221 a
`sim/` debt and the ucore reproduced the chip's grant order exactly on every
access §65.2 reached.

**NOTHING IS LANDED FROM THIS CELL** unless S2 fires and the swapped slots
carry a single mechanism.
